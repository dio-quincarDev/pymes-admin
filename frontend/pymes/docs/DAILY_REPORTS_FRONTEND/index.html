    Daily Reports — Frontend PYMEQ¶

    Registro cronológico de decisiones, problemas resueltos y estado del frontend.

    2026-11-21 — Salud financiera: Crecimiento deja de asustar¶

    Contexto: la tarjeta mostraba -45.3% vs hace 3 meses con gauge rojo en 0. En realidad comparaba noviembre a mitad de mes ($4,515.71) contra un mes cerrado (~$8,255): un -45% falso que bajaba la salud de 64 a 59.

    Qué se hizo: - financialGuide.ts — si el backend no manda revenueTrend, la tarjeta dice Aún no hay historial / Se mide con 3 meses cerrados (no lo confunde con un 0% real). Con datos, muestra Octubre vs agosto: +4.6% y debajo los montos con formatCurrency. Corregido el texto "hace 3 meses": el driver trae los meses reales. - TraderGauge.vue / FinancialHealthBreakdown.vue — GuideLine.sinDatos oculta el número del gauge y cambia el aria-label a "sin datos": mostrar un 50 inventado engañaba al usuario y al lector de pantalla (revisión con chart-designer). La aguja sigue en el centro.

    Verificación: npm run build PWA verde. Sin commit/push.

    2026-11-20 — Factura: caret sí, desplegable no¶

    Contexto: para arreglar la búsqueda de producto se cambió focus() por showPopup(). En pantallas chicas eso abre el menú con todos los productos en cuanto se pulsa "Agregar item" y tapa la factura. El problema real era que en móvil QSelect ponía el caret en un input que no era el de búsqueda (modo diálogo), no que faltara abrir el desplegable.

    Qué se hizo: - InvoiceItemCard.vue — reveal() vuelve a focus() y conserva el scrollIntoView. Causa real del "escribir no filtra": en móvil QSelect elige diálogo cuando hay @filter + slot no-option, y en ese modo el input del campo queda con no-pointer-events, así que el caret no era el input de búsqueda. Se agrega behavior="menu" para forzar el menú inline: el campo sigue editable, filter() corre al teclear y el menú abre solo las coincidencias (input-debounce="0"). - FacturasPage.vue — eliminado el parámetro openPopup de addItem()/reveal() y el @click="addItem()". El scroll y el flujo de "Agregar item" siguen igual.

    Verificación: npm run build PWA verde (lint + vue-tsc). Commit local; sin deploy todavía.

    Pendiente en dispositivo real: en iOS el navegador puede ignorar el focus() programático y el teclado sale con un toque; el filtrado sigue siendo inmediato.

    2026-11-17 — Factura: el item nuevo se revela solo + limpieza del merge de develop¶

    Contexto: con muchos items, el botón "Agregar item" queda al final del dialog y el card nuevo se inserta por encima de él, fuera del viewport visible (peor en móvil, donde además entra el teclado). Había que hacer scroll manual para llegar al campo "Buscar producto..." y escribir el nombre. Por otro lado, el merge de develop (158daba) reintrodujo itbmsMes — el KPI viejo que esta rama ya había reemplazado por "Mejor día" — y el CI falló por variable sin uso.

    Qué se hizo: - InvoiceItemCard.vue — useTemplateRef al root y al q-select de producto; defineExpose({ reveal }) con scrollIntoView({ block: 'center', behavior: 'smooth' }) + focus() del input. El hijo expone la acción, el padre no hurga el DOM. - FacturasPage.vue — handles imperativos por card (function refs en el v-for); addItem() ahora es async: push → nextTick() → reveal() del último card. openCreate() lo espera. Aplica igual en móvil y desktop. - useFinancialDashboard.ts + DashboardPage.vue — eliminadas las 3 huellas de itbmsMes (computed, export y destructuring) que develop reintrodujo; el KPI vigente es "Mejor día del mes".

    Verificación: npm run lint 0, npm run test 80/80, npm run build PWA verde, backend ./mvnw test -B 275/275.

    Pendiente de probar en dispositivo real: en iOS el focus() puede abrir el teclado antes de que termine el scroll suave; si pasa, cambiar behavior: 'smooth' por 'instant'.

    2026-11-17 — Lote 3: el semáforo de alertas deja de mentir (§8 estrategia)¶

    Contexto: el backend ya mandaba severity (CRITICAL/WARNING) desde los Lotes 1 y 2, pero el frontend la descartaba y coloreaba por código: 5 avisos críticos salían amarillos. Además el pill del Dashboard decidía rojo solo si el código contenía NEGATIVE u OVER_LEVERAGED, así que una alerta roja detrás de una amarilla pasaba desapercibida.

    Qué se hizo: - types/analytics.ts + analyticsNormalize.ts — FinancialHealthAlert.severity tipada ('CRITICAL' | 'WARNING'); el normalizador la copia del wire (WARNING solo si dice WARNING, si no CRITICAL por caché vieja). +1 test. - FinancialHealthAlerts.vue — color por severity, adiós mapa por código y adiós isGoodDependence. Se eliminó el chain de props muertas health/recommendations (componente, panel y 2 páginas) que solo alimentaba ese parche. - financialGuide.ts — borrada isGoodDependence (heurística que pintaba la concentración de amarillo con cualquier ahorro < 10%). - DashboardPage.vue — pill del semáforo por severity, no por código. - Backend AnalyticsServiceImpl — criticalAlerts ordenados CRITICAL primero antes de devolverlos; +1 test unitario.

    Verificación: npm run test 80/80, npm run lint 0 errores, npm run build PWA verde; backend ./mvnw test -B 275/275. Sin commit/push (orden del usuario).

    2026-11-13 — Dona ABC cuadra con FacturasPage + ITBMS del mes en el Dashboard + alertas sin falsas alarmas¶

    Contexto: la dona "Top productos por gasto" no cuadraba con FacturasPage (nov $949.79 vs $957.47; la diferencia exacta era el ITBMS). Las alertas de salud financiera disparaban falsas alarmas con datos reales: "Costo Diario Sobre Ingreso Diario" dividía las ventas del mes en curso entre los 30 días del mes (centinela ~200% cuando el ritmo real era ~80%), y "Erosión de Margen Bruto" comparaba un mes a medias (nov 54%) contra meses cerrados y marcaba crítico un margen sano (>30%).

    Qué se hizo: - Backend analisisABC — reparte el total real de cada factura PAGADA (ITBMS y descuento global incluidos) entre sus items proporcional al subtotal; base = SUM(invoice_items.subtotal) por factura (14 facturas legadas de septiembre tienen encabezado en 0). Filtro type = 'FACTURA' para alinear con FacturasPage. Test de integración: $100 base + $7 ITBMS = $107. - Backend DAILY_COST_CONTROL — mes en curso se compara contra días transcurridos; meses cerrados siguen con el mes completo. Título "Los gastos fijos superan tus ventas"; mensaje con montos: "Gastas $139.80 al día en costos fijos y vendes $174.01 al día." Umbral 1.2 se mantiene. - Backend MARGIN_EROSION — solo se evalúa con meses cerrados; crítica solo si el margen bruto actual < 30% (piso de margen sano que ya usa la app); si está sano, la caída va como recomendación. Mensaje: "De cada $100 que vendes te quedan $54 después de pagar la mercancía; hace 3 meses eran $74." - Frontend Dashboard — KPI "Facturas pendientes" → "ITBMS del mes" (itbmsMes en useFinancialDashboard: suma itbmsTotal de FACTURA PAGADA del período, misma regla de caja; accent azul). La lista de pendientes sigue en ActivityPanel. - Frontend CategoryBreakdownChart — total centrado + leyenda HTML táctil (mismo patrón que TopProductosDonut): leyenda Chart.js desactivada, paleta compartida arcos/leyenda, toque tacha la tajada, total = todas las categorías incluida "Otros". Código muerto _pcts eliminado.

    Verificación: backend/core ./mvnw test -B → 263 unitarios verdes (nuevos: abc_reparteTotalDeFacturaConItbms + 5 de salud financiera) e ./mvnw verify -B -Dspring.profiles.active=integration verde; frontend npm run lint 0 + npm run build PWA verde. Pendiente: recalcular 2026-11 y 2026-10 en staging tras el deploy y verificar dona $957.47 / $3,431.36.

    2026-11-11 — Alertas de salud con dinero y productos reales + barras Antes/Ahora¶

    Contexto: reproducción contra staging (tenant Mi Rinconcito Criollo, período 2026-11) vía API confirmó cuatro bugs de las alertas: "Inventario Muerto" disparaba por $26 en 5 productos sin nombres ni montos; PAYBACK_RECOVERY mostraba "Recuperación de Inversión" con métrica -1 (centinela); "Recomendaciones" repetía las mismas alertas; y en "Desvíos en Precios de Insumos" las barras "Pagaste/Suele costar" mostraban el mismo número dos veces en verde (el backend nunca manda currentPrice para PRICE_VARIATION; el normalizador copiaba avgPrice en ambas).

    Qué se hizo: - Backend AnalyticsServiceImpl — DEAD_INVENTORY ahora exige ≥ $50 de capital parado (shortcut: fijo, antes disparaba con $1), se renombra a "Productos parados" y adjunta items (id/name/totalInvestment/lastPurchaseDate) con la lista ya calculada. ## 2026-08-27 — Fix logout: redirect a landing + race condition + cache limpieza

### El problema

Al hacer logout, la app quedaba en el form de login (`AuthLayout`) en vez de ir a la landing page. Además, si el usuario hacía logout mientras un refresh de token estaba en curso, los requests encolados reintentaban con tokens ya borrados, causando un loop de 401s antes de llegar a la página de login.

### Por qué pasó

**Redirect:** `useLogout.ts` hacía `router.push('/login')` — la ruta `/login` usa `AuthLayout` (centrado, sin sidebar). El usuario quería ir a la landing page (`/`).

**Race condition:** En `src/boot/axios.ts`, el `clearSession()` local no reseteaba `isRefreshing` ni limpiaba `failedQueue`. Si un request 401a y el refresh está en curso, y el usuario hace logout al mismo tiempo:
1. `clearSession()` borra el token de localStorage
2. El refresh pendiente completa y escribe un token nuevo
3. Los requests encolados reintentan → 401 otra vez → intentan refresh sin refresh token → loop

**Cache:** El `core-api-cache` (StaleWhileRevalidate) sobrevivía el logout. Un usuario que hacía logout + login rápido podía ver datos del usuario anterior.

### Fix

| Archivo | Cambio |
|---------|--------|
| `src/composables/useLogout.ts` | `router.push('/login')` → `router.push('/')` |
| `src/boot/axios.ts` | `clearSession()` ahora resetea `isRefreshing = false` y `failedQueue = []` |
| `src/modules/auth/store/index.ts` | `clearSession()` ahora limpia `caches.delete('core-api-cache')` |
| `src/modules/auth/store/index.ts` | `auth:401` listener redirige a `/#/` en vez de `/#/login` |
| `src/boot/axios.ts` | AUTH005 redirect a `/#/?reason=session_revoked` en vez de `/#/login?reason=session_revoked` |
| `src/modules/auth/store/index.ts` | `fetchCurrentUser` catch redirige a `/#/` en vez de `/#/login` |

- `auth:401 event clears localStorage` — verifica que el evento `auth:401` limpia todas las keys de localStorage
- `re-login after logout gets fresh tokens` — verifica que después de limpiar la sesión, no quedan tokens stale

## 2026-08-27 — Fix SVG cache: logos no se actualizan en staging

### El problema

Cambiaste el logo SVG pero en staging seguía mostrando el viejo. No importaba cuántas veces redeployaras — el browser siempre mostraba la versión anterior.

### Por qué pasó

Hay 3 capas entre el browser del usuario y el archivo SVG real. Las 3 estaban guardando copias de la versión vieja por distintas razones:

**Capa 1 — nginx (dentro del container Docker):**
nginx decía "guardá este SVG por 1 año". Aunque el archivo nuevo estaba en el container, nginx seguía entregando el viejo a cualquiera que lo pidiera.

**Capa 2 — Caddy (reverse proxy frente a nginx):**
Caddy tenía un filtro para detectar SVGs y decirle al browser "no guardes esto". Pero el filtro estaba escrito con una sintaxis que no funcionaba — nunca atrapaba los SVGs reales. Entonces el browser nunca recibía la instrucción de no cachear.

**Capa 3 — Cloudflare (CDN que guarda copias para todo el mundo):**
Cloudflare guardó una copia del SVG viejo hace 7 días con instrucciones de guardarlo por 1 año. Mientras esa copia existiera, Cloudflare la entregaba directamente sin preguntarle a nadie. El browser nunca llegaba al origin.

### Cómo se arregló

1. **nginx.conf** — Se le quitó el cache de 1 año a los SVGs. Ahora dice "no cacheés nunca".
2. **Caddyfile en la instancia** — Se corrigió el filtro para que sí detecte los SVGs. El filtro viejo (`path *.svg`) no matcheaba `/icons/logo.svg` porque el `*` de Caddy no cruza `/`. Se cambió a `path_regexp \.svg$` que usa una expresión regular que sí funciona.
3. **Cloudflare** — Se purgó el cache viejo desde el dashboard ("Purge Everything").

### Lección importante

Cloudflare es el punto más crítico. Aunque arregles nginx y Caddy, si Cloudflare tiene una copia vieja guardada con TTL largo, el browser nunca ve la nueva. Cada vez que cambies algo visible (logos, icons, SVGs), hay que purgar Cloudflare después del deploy.

    Problemas¶

    2026-06-19 — Seguridad OAuth2 y replaceState¶

    OAuth2 Code Exchange¶

    Problema: AuthCallback.vue recibía JWT directamente en la URL (?token=xxx&refresh_token=yyy), exponiéndolos en el historial del navegador, URL bar y header Referer.

    Solución: El backend ahora emite un código de un solo uso (?code=xxx). El frontend lo canjea via POST /api/v1/auth/exchange. JWT nunca toca la URL.

    Impacto en UX: Ninguno — flujo transparente para el usuario.

    replaceState para limpiar tokens en hash routing¶

    Problema: Tres páginas recibían tokens sensibles por query param dentro del hash. En hash routing, window.location.hash incluye los params (#/ruta?param=valor), así que window.history.replaceState estándar no los borraba.
