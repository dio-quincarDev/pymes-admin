## Documentation: Rate Limit Service

### Technical Overview
* **Component:** `RateLimitService`
* **Infrastructure:** Redis (Atomic counters)
* **Responsibility:** Protection against brute-force and credential stuffing attacks.
* **Mechanism:** **Sliding Window Counter** (Fixed-window variation) using atomic increments.

---

### Logic & Implementation

The service provides a lightweight throttling mechanism by tracking request frequency associated with a specific key (typically `IP + Action + Email`).

#### 1. Rate Limiting Algorithm
* **Atomic Increment:** Uses `redisTemplate.opsForValue().increment()`. This ensures thread safety and accurate counting even under high concurrency.
* **Expiration Logic:** The TTL (Time To Live) is established only on the first request (`count == 1`). This starts the countdown for the specific window.
* **Window Duration:** **15 minutes**.
* **Threshold:** **5 attempts** per window.

#### 2. Key Structure
* **Prefix:** `rate_limit:`
* **Composition:** Keys are dynamically generated by the caller (e.g., `rate_limit:login:192.168.1.1:user@example.com`).

---

### Core Methods

#### `isAllowed(String key)`
* **Process:** Increments the counter and checks against `MAX_ATTEMPTS`.
* **Side Effect:** Logs a warning when the limit is breached for security monitoring.
* **Return:** `boolean` status (Allowed/Denied).

#### `getRemainingAttempts(String key)`
* **Process:** Retrieves the current counter value.
* **Logic:** Calculates `MAX_ATTEMPTS - current_count`.
* **Usage:** Primarily used to inform the user or the frontend about the remaining quota before lockout.

| Feature | Detail |

| **Time Complexity** | O(1) per check |
| **Max Attempts** | 5 |

---

### Security Considerations

#### Brute-Force Mitigation
By combining the IP address and the target email in the key, the service prevents attackers from:
1.  Testing multiple passwords for a single email from one IP.
2.  Testing one password against multiple emails from one IP (depending on key strategy).

#### Distributed Accuracy
Since the state is stored in Redis, the rate limit is synchronized across all microservice instances. An attacker cannot bypass the limit by hitting different nodes in the cluster or the Load Balancer.

#### Observability
Exceeding the limit triggers a specific `log.warn`, which can be integrated with alerting tools (ELK, Datadog, Prometheus) to identify ongoing attacks in real-time.
